# Online SID library picker validation

[`LIBRARY-1`](../PLAN.md#online-sid-library-picker-library-1) adds SIDquake’s existing HVSC browser to Explorer. The [research record](../research/sid-library-picker.md) owns provider comparisons, the reviewed protocol, terms and the original isolated handoff check. This record owns Explorer integration evidence.

## Interaction

Choose **Browse SID library** beside **Open local SID**, search in SIDquake’s dialog, choose a result and press **Select**. Explorer closes the dialog, loads the SID and shows its title, author and release. Press **Play** to start playback. **Library information** expands the credited collection path and available STIL text. Subtune, clock and chip-model controls use the existing loader.

The provider first loads when its dialog opens. The same iframe remains mounted while hidden, preserving search, the current library folder, results and scroll position across closing, selecting songs and reopening within the Explorer tab. Reloading Explorer resets this session; Explorer does not serialize provider state. Local opening does not initiate provider lookup or send files, hashes or metadata. Unsupported profiles report an error. Selection failures retain the browser state; **Reload library** explicitly starts a fresh provider frame, while local opening remains available.

Close hides the browser and preserves the current tune. Selection messages arriving while hidden are ignored, and messages from discarded frames are rejected. SIDquake supplies neither a request ID nor a selection-start event: a request begun before Close that finishes after reopening the same retained frame is indistinguishable from a new selection and can load that SID. The user explicitly prioritized retained browsing state without another confirmation step on 2026-10-20; this replaces the original discard-on-close contract. No timer or focus heuristic is used to claim cancellation that the provider cannot establish.

Use the visible **Close** button to cancel. Escape closes the dialog while focus is in Explorer; a Chrome guard established that Escape pressed inside the cross-origin provider frame does not reach the parent dialog. The provider has no cancellation-message contract. Keyboard traversal follows each browser’s native tab behavior; a fixed two-Shift-Tab return worked in Chrome but not default macOS WebKit, so no uniform shortcut from inside the widget is promised. The guards cover initial dialog focus/Escape, Close after iframe focus, and restored launcher focus. This boundary is retained explicitly instead of adding a provider fork or intercepting its document.

SIDquake owns search, collection navigation and delivery. Explorer adds no index, proxy, accounts or persistent library downloads. Provider text is inert, bounded text; the returned download URL/token is discarded. Library selections do not become publication-cleared catalog assets or verified musical annotations. Durations and provider-selected subtunes are outside this payload. The [length follow-up](#song-lengths-and-stable-fitting) obtains reference lengths separately from HVSC for library selections.

## Verification boundaries

The [receiver unit guards](../../tests/library-picker.test.ts) exercise the active-frame/origin boundary, payload types and size limits, optional metadata, ignored URLs, cancellation, focus, stale messages, timeout/retry and disposal. The [browser guards](../../tests/browser/library-picker.spec.ts) use an actual cross-origin iframe and the cleared Rambo sample through the [provider fixture](../../tests/browser/library-picker-fixture.ts). They do not depend on the hosted service.

Browser checks cover lazy loading, cancellation during playback, narrow layout, provider attribution, the existing loader’s pending state, plain-text metadata and SID-header fallbacks, reload, local/catalog replacement, wrong senders, obsolete frames, local-drop supersession, unsupported RSID/third-chip profiles, and service failure/retry. Pending loader feedback uses the shared [worker-request gate](../../tests/browser/worker-control.ts).

Live-provider smoke checks are separate from deterministic guards. They search for Rob Hubbard’s **Commando**, select it through SIDquake, load it in Explorer and verify advancing playback and measured PCM. They must use the shared silent fixture, disable trace/video/download capture, and avoid persisting SID bytes or token URLs. UI screenshots and metadata-only receipts may be retained under ignored `build/library-picker/`. A passing localhost check does not establish behavior on the deployed Explorer origin.

The initial integrated browser guard failed because the pre-feature build lacked **Browse SID library**. Logs are retained locally under `build/library-picker/`.

The complete serialized unit suite passed all 176 checks in 77.7 seconds, including the new receiver guards, browser-policy guard and existing engine/cache/profile oracles. This was a full-suite run, separate from browser emulation; focused browser runs retain their 60-second limits.

Asset preparation verified the cleared samples and existing raw-chip runtime with its licenses/notices/complete source. The final production build and TypeScript check passed. Local documentation links/fragments and patch whitespace passed. No engine build or playback-core modification was needed.

The first live Chrome check loaded and played Commando, but visual review at 390 px found that the provider’s narrow-layout `.hvsc-path-text` rule (`flex: 1 0 100%`) pushed its Select button outside the iframe. A new pre-click viewport assertion reproduced visibility ratio zero; Playwright’s automatic scrolling during click had masked it in the earlier run. Explorer now uses the provider’s documented `path=0` display option. The selected path remains available in Explorer’s Library information, and SIDquake/HVSC attribution remains visible. No provider source or styles are overridden. The [pinned embedding guide](https://github.com/RobertTroughton/SIDquake/blob/20caa381880dacbe01e139c828899f08fb3ac329/docs/EMBED.md#chrome) documents the option.

Two initial deterministic runs exposed fixture defects: tests that never played audio could not satisfy the shared silent-sink teardown assertion, and fixture buttons were enabled before their handlers were installed. The common setup now exercises real silent playback before pausing, and provider buttons stay disabled until initialized. Those failures do not establish a production loader defect. Original logs and failure diagnostics are retained; deadlines and tracing policy are unchanged.

All six deterministic scenarios passed with the configured retained-on-failure tracing and no retries: Chrome in 51.0 seconds and macOS WebKit in 30.6 seconds. Each run retained the 60-second global limit; the totals include teardown.

Four existing local-input/profile regressions passed in each browser: device-local mono loading and annotation invalidation, local dual-SID inspection, rejection of conflicting concrete models without replacing playback, and second-chip model selection with an intentional uniform override. The focused runs also exercised cancellation (Chrome: five passed in 15.2 seconds; WebKit: five passed in 18.0 seconds). The final cancellation guard explicitly verifies Escape with initial parent focus and Close after focusing inside the frame; its final Chrome check passed in 5.9 seconds, and the WebKit run includes that final form.

The final live-provider checks passed in Chrome `155.0.8059.85` (17.2 seconds) and macOS Playwright WebKit `26.0` (9.1 seconds). Both searched through the real widget, selected Commando, loaded its Rob Hubbard / 1985 Elite metadata and 19 subtunes, then measured nonzero PCM and an advancing heard position in Explorer. Screenshots at 1440 px and 390 px were inspected; the narrow Select button and SIDquake/HVSC attribution remained visible. There were no page errors. These checks used the shared zero-gain audio fixture with trace/video/download capture disabled; only UI screenshots, sanitized request timings and metadata receipts were retained.

Two intervening live attempts failed at the five-second handoff assertion and the fifteen-second search-result deadline. Those earlier runs did not retain enough network timing to establish their causes. The final harness waits for the provider’s ready signal before searching and records only request paths/timings and message types/sender matches, never token URLs or SID bytes. Successful final runs demonstrate the workflow, not guaranteed provider availability or performance.

Actual Safari and recent-iPhone acceptance, deployed-origin verification and publication remain separate gates. Earlier stereo acceptance does not establish this new third-party workflow.

## Retained browser session follow-up

The user required session-only reuse on 2026-10-20 after rejecting a proposal to defer retention or add another selection confirmation. Close, Escape and successful selection now hide the same iframe. Selection failures keep it available; explicit **Reload library**, invalid active payloads or a failed startup discard it. Readiness arriving while hidden settles the original startup deadline; reopening does not extend that deadline. Disposal removes the frame, timer and listeners.

The focused receiver run was red with 9 of 34 checks failing against discard-on-close, then green with all 34 passing. The combined receiver/browser-policy run passed 35 checks in 0.55 seconds. The browser retention guard failed against the old preview because closing removed the frame; it now asserts retained frame presence before attempting hidden-message delivery. In both Chrome and macOS WebKit the four lifecycle scenarios passed (12.4 and 12.5 seconds): one iframe, retained search/folder/results scroll across close and selection, hidden-message rejection, explicit reload invalidation, failure recovery and reset after Explorer reload. The other three loading/profile cases passed in each browser (six checks in 20.1 seconds). These runs retain configured tracing on failure, silent audio sinks and no retries. Asset preparation, production build, documentation and whitespace checks passed. Evidence is under ignored `build/library-retention/`.

The first live retention check kept the query and folder and loaded Commando, but its extra assertion that the selected-row highlight survives subsequent playback failed. Provider source and sanitized network timings establish the separate mechanism: completion of `hvsc-stil.json` reruns `runSearch()`, which clears `currentSelection` before repainting. This can change results/highlighting independently of Explorer closing the dialog. A second live attempt caught the same refresh between selecting a row and pressing Select, leaving the dialog open without a handoff. The final harness waits for parsed STIL entries through the provider’s read-only index accessor before selecting; it does not use a delay or modify provider state. The live oracle checks the requested query, folder, search result presence and single iframe load; it does not promise that Explorer freezes provider updates. The deterministic fixture separately verifies that closing/reopening itself preserves result scroll position.

The final live-provider retention checks passed in Chrome `155.0.8059.85` and macOS Playwright WebKit `26.0` (two checks in 15.5 seconds). Each navigated to `MUSICIANS/H`, closed/reopened with the folder intact, searched for Commando, closed/reopened with the query intact, loaded and silently played the real SID, then reopened with the search still present. Each observed exactly one provider iframe request and no page errors; attribution and Select remained visible at 1440 px and 390 px. Music bytes stayed in browser memory; only sanitized logs, UI captures and metadata receipts were retained. This remains automated localhost evidence, separate from actual Safari/iPhone and hosted-origin acceptance.

## Separate pre-existing finding

Source review found that [application startup](../../src/main.ts) disposes the player on `pagehide`, including navigation into the browser’s back/forward cache. Returning to that cached page may restore a disposed player. This feature closes the picker on `pagehide` without permanently disposing its controls; changing the player’s existing navigation lifecycle is outside `LIBRARY-1`.


## Song lengths and stable fitting

On 2026-10-20 the user approved HVSC duration lookup, required an honest unknown-length mode for manually opened files, asked about continuous-rescaling efficiency and rejected the word “explored” in the UI. Library loads now obtain an optional reference duration from the [official HVSC database](https://hvsc.c64.org/download/C64Music/DOCUMENTS/Songlengths.md5) before entering the existing player load path. Original file bytes are hashed locally with MD5 and matched to the selected 1-based subtune using the existing `SonglengthDatabase` parser. Explorer’s engine changes the start-song header during loading, so hashing its altered bytes would break the lookup after changing subtunes; [lookup guards](../../tests/song-lengths.test.ts) compare against Node’s independent MD5 implementation.

Only library selections invoke lookup. The fixed database GET contains no song, path or hash query, omits credentials/referrer, and shares one in-flight/successful parsed database per Explorer tab. Local files do not fetch or use it, including after a library selection. HTTP errors, timeout, invalid data, absent entries, incompatible clock overrides and lengths outside the existing positive 600-second playback range fall back to unknown. Failures are retried only by a later explicit library load. Download/body handling has an eight-second deadline, an eight-MiB limit and cancellation on oversized/invalid streams. No database is bundled or mirrored. The source check found a CORS-enabled GET of 5,205,150 bytes and 61,157 entries; the server disables HTTP caching, hence the application cache. One Node 24.18.0 parse measurement took 174.616 ms; this is a one-time metadata cost, not a browser frame-time benchmark.

Known durations retain **Fit song**. Unknown durations use **Fit timeline**: clicking captures the current timeline range, whose scale stays fixed as playback and preparation advance; clicking again explicitly refits it. The scrollbar shows the current limit with **length unknown**, distinct from the chart’s fitted endpoint. Switching sources resets the captured range; seeking does not. Local-file metadata and playback remain on-device.

The continuous-rescaling investigation found that `setTimelineOverview()` reset its request timestamp whenever the endpoint changed, bypassing the existing one-second throttle. The [player regression](../../tests/player.test.ts) produced 101 overview requests in a simulated second before the fix and two afterward (initial request plus the update at 1000 ms). Changes coalesce into the next request; stale replies remain rejected. The fixed unknown-length range also removes the source of continuous rescaling. Existing playing UI draws remain limited by the 70-ms scheduling gate; overview extraction reads bounded sampled history rather than executing the SID again. These are request-count and source-level bounds, not measured device CPU/FPS claims.

The first browser integration run found an unbound native fetch invocation being caught as unavailable metadata; a receiver-sensitive default-fetch regression reproduced it and binding to `globalThis` fixed it. The same run found test assertions comparing unrounded durations to two-decimal accessibility strings; the guards now independently check exact seek limits and formatted chart limits. The packaging guard detected the added MIT notice and now verifies its exact upstream contents. Failure logs remain under ignored `build/song-length-ui/`; the existing engine binaries and emulation core were not changed.


Final focused validation passed: 12 lookup, 29 player, one browser-policy and two packaging guards; the packaging pair was rerun after extending its notice inventory. The five duration/fitting scenarios passed in Chrome (53.1 seconds, including teardown) and macOS WebKit (14.0 seconds). Three existing picker regressions passed in each browser (six checks in 24.2 seconds). A strengthened privacy guard then reopened the exact database-matched library bytes as a local file and verified unknown duration without another request in both browsers (8.3 seconds). Asset preparation, production build, local documentation links/fragments and patch whitespace passed. The production JavaScript grew by approximately 7.7 kB uncompressed / 3.2 kB gzip for lookup, parsing and MD5; the audio engine was not rebuilt.

The live-provider check passed in Chrome `155.0.8059.85` and macOS Playwright WebKit `26.0` (18.7 seconds combined), using the official database GET from the local Explorer origin. Both loaded and silently played Commando, verified exact seek limits of 235.594 seconds for subtune 1 and 61.288 seconds after reloading subtune 2, and retained the library browser state. There were no page errors. Music stayed in browser memory with trace/video/download capture disabled. Actual Safari/iPhone and the published Explorer origin remain separate acceptance gates.

## Source controls and repeated selection

On 2026-10-20 the user reported that the unloaded app claimed Rambo was loaded. `applyCatalogDefaults()` copied the selected sample into the playback heading before loading. The [initial-state guard](../../tests/browser/initial-song-state.spec.ts) reproduced that error; catalog selection now only configures the pending sample, and source/hardware/output badges wait for actual loaded information. Changing the sample selection also preserves the metadata of a currently loaded tune.

The local file control was a label inheriting 12-pixel label styling while the adjacent library button inherited 16-pixel button styling. It is now a native **Open SID file** button with consistent styling inside a visible **or drop a SID file here** target. File drags highlight that target; the existing page-wide drop intake still accepts files through the same local validation path. The [file-control guard](../../tests/browser/local-file-control.spec.ts) opens the native chooser, loads a cleared SID, drops a different cleared SID and verifies playback, spacing and narrow layout. Both guards were red before implementation and passed in silent Chrome and macOS WebKit afterward (four checks in 18.5 seconds). Desktop and narrow screenshots were inspected; logs/captures are under ignored `build/song-state-fix/`.

The reported failure to replace a library song was not reproduced. Two live Chrome checks replaced Commando with Monty on the Run in the same retained iframe, including replacement during active playback. Sanitized handoff paths/titles, the new header/path and advancing nonzero PCM confirmed the second selection; the active-playback check took 12.3 seconds. The user subsequently confirmed replacement works. No production picker or loader change was made. Coverage now uses distinct cleared Rambo and Bach bytes rather than selecting the same fixture twice, including header-derived metadata without a supplied title. This does not establish the cause of the original report or a new Safari/iPhone verdict.

The receiver suite passed 35 checks, including distinct retained-frame payloads. The new [replacement browser guard](../../tests/browser/library-picker.spec.ts) passed in Chrome and macOS WebKit (two checks in 15.2 seconds), verifying one iframe, new header-derived metadata/path, reset playhead and subsequent advancing PCM. The production build passed. Sanitized live logs and deterministic results are under ignored `build/library-picker/`.
