# Playback adapter

The accepted mono prototype used the unchanged npm `libsidplayfp-wasm` 1.1.0 SIDLite artifact through its low-level `SidPlayerContext`. Dual-SID implementation adds a separately built raw-chip binding; [its validation record](../validation/stereo.md) owns adoption status. [The founding design](../design/web-player-and-analyser.md#first-step-and-milestones) owns the product gates. This adapter produces emulated PCM and chip-indexed observations; browser scheduling, heard-position tracking and interaction belong to the application transport. Successful rendering does not establish Safari speaker playback or human listening acceptance.

## Application shell decision

Use a small TypeScript/Vite shell over the existing WASM engine for this mono POC. The retained [Chip Player JS review](../research/web-music-explorers.md) found application-service coupling and no existing trace contract; the immediate question is whether this binding can provide consistent audio, stateful replay and useful observations. Reusing its larger application shell would not settle that question. Explorer therefore reuses the emulator and implements only transport, inspection and source-linked presentation. This is a bounded POC decision, not approval of dual-SID routing or every SID file profile.

Node 24.18.0, pnpm 11.20.0, TypeScript 5.9.3 and Vite 7.3.1 form the development toolchain. Vite uses ES-module workers because the upstream loader imports engine modules dynamically. Its browser build externalizes the loader's Node-only `module` import; production-browser checks exercise the browser branch. The modified artifact’s complete corresponding source, licenses, notices and modification record are verified and prepared alongside the deployment assets by [prepare-runtime.ts](../../scripts/prepare-runtime.ts).

## Supported input and configuration

[SidSession](../../src/engine/session.ts) accepts PSID versions 1–4 with the standard 118/124-byte header, one or two SIDs, a nonzero callable play address, 1–256 songs and a program that fits C64 memory. Both VBI and CIA-timed callable PSID execute through libsidplayfp's driver. The caller explicitly selects PAL/NTSC, MOS6581/MOS8580 and a one-based subtune; these choices override header clock/model suggestions. Local file contents remain inside the worker.

Preflight rejects RSID, MUS payloads, PlaySID-specific compatibility flags, third SID chips, invalid second-chip addresses, interrupt-driven `play=0`, malformed offsets/counts and files above 65,662 bytes before constructing a WASM context. This is a declared subset, not general SID-format support. An initial SID write must appear within 20,000 single-event startup probes; a valid program with a longer delayed initialization can therefore be rejected. A later halt or failure to produce samples returns an execution error. No system ROM files are loaded or distributed; supporting ROM-dependent programs requires a separate scope and rights decision.

The output is 44,100 Hz signed 16-bit PCM, mono for one chip and interleaved stereo for two, with SIDLite's filter implementation. `LoadResult.engine` reports the actual builder, libsidplayfp version, CIA model, sampling method, digi boost, effective startup delay and trace timing basis. With this pin, executed checks report `WasmSIDLite`, libsidplayfp 3.1.1, `MOS8521`, `RESAMPLE_INTERPOLATE` and digi boost enabled. The selected SID model on every installed chip, chip count/addresses, C64 model and sample rate are checked against the resolved engine configuration before accepting a load. The stock mixer stays configured mono; the additive raw method independently returns one channel per installed chip. SIDLite does not expose reSIDfp's analogue filter tuning.

The requested power-on delay is always zero. Upstream [Player::initialise](https://github.com/libsidplayfp/libsidplayfp/blob/732fa8ec8131fc75aafc2eaea583ddcdeea2a3cc/src/player.cpp) adds 8000 internally, so the effective delay reported by the engine is 8000. Zero here selects deterministic startup; it does not mean the emulation begins with zero startup work.

## Session and worker contracts

```typescript
const session = await SidSession.create({ moduleUrl, wasmUrl }); // verified runtime URLs
const info = await session.load(bytes, {
  clock: 'PAL', model: 'MOS6581', subtune: 1,
});
const block = session.render(4096);
const position = await session.seek(12.345);
await session.mute([false, true, false]); // true means muted
session.dispose();
```

`create` is lazy: input preflight happens before the WASM loader is invoked. `render(frames)` accepts integer counts from 1 through 88,200 and returns `{pcm, startFrame, endFrame, writes, registers, dropped}`. The counters describe PCM delivered to the caller, rather than how far the underlying context has already emulated. `seek(seconds)` accepts finite positions from zero through 600 seconds, converts to `floor(seconds * 44100)`, reloads deterministic initialization and consumes every preceding frame. It preserves the final raw block remainder. `mute(mask)` performs the same replay to the consumed frame with the new three- or six-voice mask, so buffered PCM cannot retain the previous mask. Restoring the full mix replays its full history rather than inheriting a muted filter/envelope history. Muting remains an engine intervention, not a promise of isolated stems or preserved cross-voice dependencies.

The session caller must serialize methods. [The worker](../../src/engine/worker.ts) supplies that boundary with request/reply messages defined in [the protocol](../../src/engine/protocol.ts):

| Method | Payload | Result |
| --- | --- | --- |
| `load` | `{bytes: Uint8Array, options: PlaybackOptions, durationSeconds?: number}` | `LoadResult` |
| `render` | `{frames: number}` | `RenderResult` |
| `seek` | `{seconds: number}` | `{frame, registers}` |
| `observe` | `{startSeconds: number, endSeconds: number}` | `TimelineObservation` or `null` when no retained coverage is available |
| `mute` | `{mask: [boolean, boolean, boolean]}` | `{frame, registers}` |
| `dispose` | none | `null` |

Every request carries numeric `id`; load/mute requests also carry the client’s `cacheEpoch`, which invalidates older coverage even when an earlier request was rejected. Replies are `{id, result}` or `{id, error}`. PCM buffers transfer to the main thread. The worker imports the SIDLite WASM URL using Vite's `?url` mechanism; the session itself has no bundler-specific imports and runs directly in Node. The worker accepts at most 16 pending requests and rejects further requests instead of growing an unlimited execution backlog. A disposed worker session may be recreated by a later load.

## PCM, trace timing and coverage

The raw binding returns a view into WASM memory; the adapter copies each PCM chunk before any subsequent WASM call. It consumes that copy exactly once and retains its unconsumed suffix. It never advances by an estimated frame count or truncates the last seek block. This avoids the final-block loss in the published [SidAudioEngine.fastForwardContext](https://github.com/chrisgleissner/libsidplayfp-wasm/blob/c9622e9ce7ffa2ddd3e0568e987b4c6614da8275/src/player.ts).

Raw `cyclePhi1` is preserved unchanged. Addresses remain SID register offsets `0x00`–`0x1f`, and `sidNumber` is zero for this mono adapter. These are ordered writes observed at the binding's [write hook](https://github.com/chrisgleissner/libsidplayfp-wasm/blob/c9622e9ce7ffa2ddd3e0568e987b4c6614da8275/src/bindings/bindings.cpp), rather than frame-polled snapshots or an assertion about the unmodified program under mute. Reset/calibration execution is separate from the actual playback trace.

The scheduler cycle counter includes startup and has no exposed cycle-zero accessor. The integer-millisecond playback accessor cannot recover its exact origin. A bounded dry pass renders one scheduler event at a time until the first SID write, counts the produced PCM, and records `traceCycleOrigin = firstWriteCycle - producedFrames * pcmClockHz / 44100`. Derived time is `(cyclePhi1 - traceCycleOrigin) / pcmClockHz`. SIDLite quantizes its sample clock to four fractional bits: `pcmClockHz = floor(trunc(clockHz) * 16 / 44100) * 44100 / 16`, starting from the pinned upstream [PAL/NTSC clock values](https://github.com/libsidplayfp/libsidplayfp/blob/732fa8ec8131fc75aafc2eaea583ddcdeea2a3cc/src/c64/c64.cpp). For this engine/rate, the resulting PCM clock is 983981.25 cycles/s for PAL and 1022568.75 for NTSC. This conversion follows generated PCM; raw CPU cycles remain unchanged. Using the nominal clock here accumulated drift and let later render calls deliver observations from earlier PCM intervals. Both startup origin and timestamp conversion must use the same PCM clock. The [seeking study](../research/seek-performance.md) retains the independent raw-render oracle and the failed one-sided correction. This is calibration to a quantized audio sample boundary. It does not establish exact analogue/resampler latency or cycle-perfect alignment with sound heard from speakers.

For the tested PAL/MOS6581 Rambo main export on 2026-10-18, the first observed write was cycle 167873 after two produced calibration frames, yielding estimated origin 167828.375 with the corrected SIDLite PCM clock. This illustrates the observed offset; the adapter recalibrates each selected configuration instead of hard-coding that tune's origin.

An independent raw-library PCM comparison found that continuing the live stream after small calibration renders changed later SIDLite samples, despite preserving their count. The adapter therefore resets the context after calibration and starts the actual stream from frame zero using its normal 20,000-event render calls. The actual startup PCM is included in full. The raw-library oracle checks that the resulting first second is byte-identical to ordinary uncalibrated raw rendering; same-session continuous/replay comparisons separately verify seeking and mute restoration. Render-partition sensitivity belongs to this engine pin, not a claim about physical SID behavior.

Returned writes cover the delivered frame interval according to the calibrated time basis; later writes from a partially consumed raw block remain pending. `registers` is a 32-entry array of the last observed register writes at that logical endpoint, initialized from the reset status. It is not a future raw-block endpoint snapshot, and it does not poll changing read-only oscillator/envelope values. The application must retain its own bounded observation history and label the calibration basis. No trace retention beyond the pending raw block is hidden in this adapter.

The dropped-record count is read before draining the binding because draining resets it. Counts are returned once and aggregated per underlying render work; an overflow cannot be attributed more precisely to a subrange of an already generated PCM block. After seek or mask replay the caller starts a fresh observation interval; replayed history is not returned as newly heard writes. A reset register image is not evidence that every initialization/hardware-reset write was traced.

## Bounds and verification

Every risky raw render advances at most 20,000 scheduler events; upstream also clamps the requested render size to 20,000. A render has a sample-production call budget and an empty-result limit, so a stopped or malformed program cannot spin indefinitely waiting for PCM. Render, startup calibration and replay check a 15-second execution deadline. Replay yields to the worker event loop after each eight seconds of emulated audio. There is no in-protocol progress or cancellation message in this prototype; terminating the worker cancels an operation immediately, while ordinary queued disposal waits behind the bounded current request. Rendering after a partial execution failure requires reloading.

[The engine tests](../../tests/engine.test.ts) use the prepared, hash-verified public Rambo asset without a sibling-checkout dependency. Run `pnpm prepare:samples`, then `node --experimental-strip-types --test tests/engine.test.ts`. A local ignored `build/engine-tests/rambo-loader-main.sid` can serve as an explicitly prepared fixture during development. The focused test budget is 60 seconds.

Executed on 2026-10-18 with Node 26.10.0: ten tests passed in 32.34 seconds under concurrent development load. Guards cover malformed/unsupported input before WASM loading, real advancing mono PCM and ordered writes, raw-library PCM equality, callable CIA execution, split blocks, exact non-block seek PCM/write equality, NTSC/MOS8580 mask restoration, finite resource bounds, a CPU-halting play routine, and the full 193.35884353741497-second main export plus a one-second tail. The full-form render verifies execution and a decayed tail, not a listening verdict or equivalence to Crafter's different renderer. Browser scheduling and Safari validation are separate application checks.

## Seeking performance work

The [seeking study](../research/seek-performance.md) owns measured alternatives, retained negative results and the bounded-cache recommendation. The low-level session still provides deterministic replay as an oracle and fallback; the application worker uses the cache layer to reuse already produced PCM and observations rather than repeatedly emulating the same passage.

[CachedSidSession](../../src/engine/cached-session.ts) separates the logical read cursor from one producer frontier. A seek within retained history selects an exact sample without executing the emulator; a forward miss executes only the missing interval; a miss behind retained history uses deterministic replay. Returned PCM is copied before worker transfer so transferring a response cannot detach retained audio. Matching ordered writes and register baselines come from the same execution as the PCM.

The default cap is 32 MiB of typed storage: PCM, five Float64 fields per write, block register baselines and frontier registers. Metadata is separately bounded to 4096 blocks; this is not a total JS/WASM process-memory cap. Background preparation produces at most 0.25 seconds per timer turn, yields to queued foreground requests and reserves conservative space before execution. It stops before evicting unread audio. Consumed history may be evicted; the UI reports the actual retained interval. A declared duration caps preparation at that duration or ten minutes; unknown-duration local files prepare at most thirty seconds ahead of the read cursor, within the ten-minute window.

Load/profile and mute changes invalidate cached audio. Mute rebuilds the changed mix only to the logical cursor, not the potentially distant producer frontier. Pending seek destinations survive a concurrent mute change. Coverage events are `{event: 'cache', coverage: {epoch, startFrame, endFrame}}`; the client discards stale configuration epochs and clears the displayed range immediately on invalidation. An idle worker failure enters an explicit error state, and a terminated client rejects subsequent work immediately. Valid cached audio remains readable after a background producer failure, but uncached execution can still fail and require reloading.

## Prepared timeline observations

`observe` reads retained cache data without rendering, seeking, advancing either cursor or copying PCM. Its result contains the actual half-open `[start,end)` interval, sampled register frames, ordered writes and a conservative dropped-write count from intersecting source blocks. The final frame describes state immediately before `end` for drawing; it does not make that endpoint inspectable. An origin query preserves initialization writes with negative calibrated timestamps, matching the existing render contract.

Each query lies within the supported 0–600-second timeline and returns at most 20,000 writes and 1,001 register frames. Samples are evenly spaced, approximately every 20 ms for short windows and coarser for wider windows to preserve the frame limit; ordered writes remain exact. If the write limit is reached, coverage ends at the first omitted timestamp and all writes at that timestamp are excluded; an explicit continuation marker distinguishes this packet boundary from unavailable source data. The player joins up to ten adjacent packets into one preview, retaining at most 200,000 exact writes and selecting at most 1,001 existing register frames, including both endpoints. It stops at a source gap, frontier, invalidated request or aggregate limit. Viewport changes stop further pagination while the existing overlap policy may admit a useful completed prefix. Missing, evicted or unprepared regions remain unavailable. The preview does not alter the cache's 32 MiB typed-storage cap; copied response objects and held UI snapshots are separate bounded memory. [The mono validation record](../validation/mono-poc.md#centered-timeline-spike) owns the initial measurements; [dense stereo validation](../validation/stereo.md#dense-timeline-observations) owns pagination evidence and cost.

Fit song uses a separate `overview` query over the whole supported duration. The producer retains original register states on a 20 ms grid independently of the selected UI mode, so the first overview request after PCM eviction still includes the beginning. The archive covers the supported ten minutes with fixed typed storage of 960,096 bytes for mono or 1,920,192 bytes for stereo, including two endpoint snapshots; this is separate from the unchanged 32 MiB PCM/write cache cap. Same-configuration backward seeks preserve it; load, mix replacement and disposal clear it. The response carries no ordered writes and selects at most 1,001 original frames. Queries wholly inside the detailed cache retain exact register-baseline sampling shared with `observe`; archived-only queries return actual retained sample times without interpolating missing endpoints or bridging gaps. The player refreshes it only when coverage/configuration/range changes, at most once per second for an unchanged range, with one request in flight. Selected sound settings use bounded exact observations, never interpolation from overview frames. Connected same-configuration overviews retain captured activity across audio-cache eviction, still bounded at 1,001 original frames; gaps are not bridged. Held overview and selected exact data are captured separately. [Whole-song validation](../validation/mono-poc.md#whole-song-overview) owns the dense-input oracle and navigation evidence.

The UI derives the visible span from drawable CSS width divided by the selected density (16–1,024 pixels per second in factor-of-two steps; default 64). Follow requests half that span behind and half plus one second ahead at most once per 250 ms. Browsing uses an independent viewport center, five seconds of extra observations on each side and a 100 ms refresh interval. Both modes permit one request in flight, after audio scheduling work. The extra second keeps the moving right edge inside prepared observations between refreshes. A direct timeline seek anchors the displayed range independently of the heard cursor. While paused it stays fixed. In Scroll, the viewport remains fixed while a left-side playhead advances to center, then resumes centered following; a right-side clicked line is pinned to the seek destination while the viewport advances exactly with heard time. It is labelled as a seek point rather than heard playback during this transition. Transport time, shading and live inspection retain the actual heard position. When the pinned line reaches center, the anchor is released and ordinary heard-centered following resumes, shifting the viewport forward by the elapsed return interval. Left-side seeks retain ordinary heard tracking against the stationary viewport until center. Fit retains its whole-song range through seeking and advancing playback. The UI expands the observation span around heard playback to cover an offset Scroll range; this remains a Follow request with the existing song-duration and coverage limits. Explicit Follow clears the anchor immediately. Zoom, resize and browsing retain valid same-configuration observations. An obsolete view reply is accepted only when it improves coverage of the current visible interval; ties and worse coverage retain the current snapshot. This permits updates during a continuous drag without allowing replaced audio/configuration replies back in. View changes neither restart transport nor bypass their mode’s refresh throttle. Known duration and the ten-minute local limit bound all requests. Both Follow and browsing show linear song material beyond loop B. A loop changes audio scheduling, not the song coordinates or validity of prepared observations; the UI labels the continuation and loop return. Seeks invalidate pending replies but retain accepted observations from the unchanged file/profile/mix until refreshed, avoiding a blank chart during the transition. The retained response remains bounded evidence even if the cache has since evicted its source range; it does not certify current prepared-cache availability. Mix changes, load, terminal errors and disposal clear preview data; replies must still match the active transport generation and engine. Request deadlines notify the fatal-error path even when the request came from idle background inspection. Prepared observations and heard history remain separate in the UI, including held copies; current inspection can use heard history when a dense preview ends before the heard cursor.


## Dual-SID runtime boundary

The additive raw-chip binding and adoption evidence are owned by [dual-SID validation](../validation/stereo.md). It preserves the existing 20,000-cycle render partition and exposes chip-order interleaved PCM from one shared C64 instance. The worker loads the separately built, verified SIDLite artifact; the stock package remains the independent mono oracle. [The native runner](../../scripts/experiments/stereo/run.py) owns reproducible source preparation and bounded compiler stages, and [runtime preparation](../../scripts/prepare-runtime.ts) refuses missing, changed or unverified artifacts. CI builds the artifact on Linux once; Chrome/Linux and WebKit/macOS consume that same artifact and corresponding source.

`LoadResult` reports `channels: 1 | 2` and actual `sidChipBases`. All positions and render lengths remain PCM frames; only the PCM array is interleaved. Registers use `chip * 32 + localRegister`, while ordered writes retain separate chip/address fields. Cache byte accounting and copies scale with the channel/register count without increasing the 32 MiB cap. Web Audio receives one channel for mono and two for dual-SID, with chip 1 left and chip 2 right. A unity-gain output path feeds the destination; a separate channel splitter feeds independent L/R analysers without a second audible path. Mono displays one channel. [The stereo validation record](../validation/stereo.md#channel-aware-audio-output) owns monitor measurements and layout evidence.
