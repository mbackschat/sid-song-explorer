# Web music players and analysis interfaces

Research recorded 2026-10-16 for the [web player and arrangement analyser proposal](../design/web-player-and-analyser.md). This is the durable record of the comparison across seven external references and the user's Williams Sound Explorer, including alternatives, adoption constraints and design lessons. The proposal owns the selected product contracts; its [pinned dual-SID review](../design/web-player-and-analyser.md#dual-sid-source-review-2026-10-16) retains the separate playback-library findings for libsidplayfp-wasm, WebSID and exact chip-bus routing.

## Question, evidence and conclusion

The question was whether an existing application already provides the desired experience, which interactions we should borrow, and whether a project-specific tool would add enough value to justify adapting or assembling it. Evidence consists of primary manuals, upstream source and author documentation. No applications were operated for this comparison, and no implementation effort, audio equivalence or Safari compatibility was measured. Later user-supplied Chip Player JS screenshots provide visual evidence only. Moving upstream links below describe the review date; the Chip Player JS review is pinned to [e90f505ccea598fb91cf08b02c4dbb41f0785632](https://github.com/mmontag/chip-player-js/tree/e90f505ccea598fb91cf08b02c4dbb41f0785632).

**Assessment:** a player with meters, scopes and mute controls would add little distinctive value. The stronger project contribution is linking a heard event to its observed behavior, verified instrument program, arrangement role, hardware dependencies, evidence and editable reuse example. Williams Sound Explorer supplies a relevant precedent for individual sound/instrument-program inspection, only one part of that experience. Whole-song form, recurring instrument use, changing roles, voice sharing and stereo arrangement require a broader musical analysis layer. This is useful project fit, not a novelty claim. Inspect Williams for reusable sound-inspection components, while comparing a Chip Player JS shell adaptation against a small project layer over a suitable engine API. Keep DeepSID as a conditional alternative. Neither the application base nor the technology stack is selected.

## DeepSID: immediate SID inspection

DeepSID's Piano view connects waveform-coloured keys with pulse width, filter cutoff/resonance/routing and ring/sync indicators. Gate/noise visibility options help with brief events. Numeric controls mute, with modifier shortcuts for solo. Multi-SID Piano combines voices into chip keyboards and changes those buttons to chip controls. Stats offers tentative movement detection, including vibrato/slide and repeated pulse/filter changes, but covers only the first chip and warns about buffering sensitivity. STIL/Player tabs add contextual information. The mobile FAQ describes hiding the right text pane. [Application help and FAQ](https://deepsid.chordian.net/).

Graph offers row/column layouts, pulse-width indicators, filter colouring, optional modulation graphics and six/nine-voice displays. Click-mute and modifier-solo connect displays to listening. Reviewed `animateGraph()` samples registers on animation frames and shifts canvas pixels; `initGraph()` clears/recreates the display. This establishes a rolling sampled visualization, not a time-indexed event archive. Mobile checks suppress it. [Change history](https://deepsid.chordian.net/changes.htm), [visualization source](https://github.com/Chordian/deepsid/blob/master/js/viz.js).

Borrow the close connection between visible activity and audible experiments. Extend it with six stable chip/voice identities and retained selection. Neither sampled animation nor diagnostic scopes establishes recovered score, complete ordered writes or isolated post-filter stems. Retained-history navigation was not established in the reviewed material; that is a bounded finding, not proof of absence throughout the app. The author's account of feature overload and external-service delays supports keeping the main experience focused, but is not an independent usability study. [Author reflection](https://blog.chordian.net/2022/05/07/the-story-of-deepsid/).

Reuse has concrete costs. `SIDPlayer` and `Viz` provide separable objects, but reference shared globals, jQuery and fixed DOM elements; no standalone analyser-component contract was established. Setup requires PHP/MySQL and collection databases. Metadata paths include `php/info.php`, including a synchronous AJAX path. The local-test file handler posts file bytes to `php/upload_test.php`; separate collection upload requires login and describes shared files. Those behaviors need replacement for static hosting and device-local opening. [Setup](https://github.com/Chordian/deepsid/blob/master/README.md), [player source](https://github.com/Chordian/deepsid/blob/master/js/player.js), [file handler](https://github.com/Chordian/deepsid/blob/master/js/main.js), [collection upload](https://github.com/Chordian/deepsid/blob/master/upload.txt).

No application-level LICENSE/COPYING or blanket reuse grant was located in the reviewed complete repository tree, README or relevant headers; located COPYING files belonged to the sidinfo utility. Permission is unresolved, not proven forbidden, and bundled-library terms do not establish application terms. Static adaptation, permission, exact stereo and Safari remain unverified. [Repository](https://github.com/Chordian/deepsid), [recursive tree endpoint](https://api.github.com/repos/Chordian/deepsid/git/trees/master?recursive=1).

## JSIDPlay2: distinguish notes from writes

The desktop guide documents persistent transport/tabs/status, local files, Oscilloscope, note-oriented SID Dump and timed SID Registers capture. Exports distinguish note-sheet CSV from writes-and-timing CSV; status includes chip models/addresses, speed and time, with player identification and up to nine voice-mute shortcuts. Borrow separate readable-event and exact-write inspection depths, linked by one time selection. The separately offered browser WASM/JS player does not establish browser parity with these desktop tools. Scope tap points, history behavior, stereo routing and Safari were not verified. [Desktop guide](https://haendel.ddns.net/~ken/UserGuide.html), [project and browser edition](https://haendel.ddns.net/~ken/).

## SID Factory II: occurrence to program

The song overview supports position jumps and double-click playback. Three voice tracks contain independently sized sequences with note, instrument and command columns. Selecting an instrument/command highlights occurrences; table pointers navigate into waveform, pulse and filter definitions. Three pulse-width bars accompany one shared filter bar, with filtered-voice indication. Bookmarks recall positions. These interactions connect arrangement position, sound identity and editable definitions, while driver-specific table meanings remain explicit. [Official manual, pp. 5–12](https://files.chordian.net/sf2/SIDFactoryII_20260314_User_Manual.pdf).

Human-readable descriptions and contextual help complement numeric editing. Borrow occurrence → program → recipe navigation, with readable names rather than requiring hex-table literacy. SF2 owns source structure; this does not imply arbitrary SID binaries supply instrument IDs or recoverable tables. No interactive session was run; PDF screenshot extraction failed, so findings rely on manual text and author documentation. [Author release notes](https://blog.chordian.net/sf2/).

## Furnace: aligned parameters and chip ownership

Furnace separates order/channel overview from note/instrument/volume/effect patterns, with optional names and channel/status hints. Playback-following can be toggled separately for orders and patterns; transport includes pattern repetition and row stepping. Borrow inspection that can stop following playback without losing the heard position. [Order list](https://tildearrow.org/furnace/doc/latest/2-interface/order-list.html), [patterns](https://tildearrow.org/furnace/doc/latest/3-pattern/index.html), [transport documentation](https://raw.githubusercontent.com/tildearrow/furnace/master/doc/2-interface/play-edit-controls.md).

Macros show numeric sequences with shared horizontal scrolling, tick lengths, delay, loop/release points and relative/fixed pitch; other types include ADSR and LFO. SID controls expose waveform, envelope, PWM, ring/sync and filtering, with chip-global volume explicitly documented. Scopes can carry channel/note/instrument/chip labels; raw register inspection is separate. Borrow aligned parameter lanes and visible shared resources, while distinguishing programmed automation from observed trajectories and measured amplitude. [Instrument editor](https://tildearrow.org/furnace/doc/latest/4-instrument/index.html), [SID instruments](https://github.com/tildearrow/furnace/blob/master/doc/4-instrument/c64.md), [scopes](https://github.com/tildearrow/furnace/blob/master/doc/8-advanced/chanosc.md), [register view](https://tildearrow.org/furnace/doc/latest/8-advanced/regview.html).

The online manual may describe development features; no installed release was tested. Current macro-step highlighting was not established. Furnace is a source-aware desktop editor precedent, not evidence of automatic SID recovery or a browser application base. [Manual notice](https://tildearrow.org/furnace/doc/latest/).

## Sonic Visualiser: retain the passage under study

Time-aligned panes/layers can share zoom/scroll with per-pane opt-outs. Playback follow can page, scroll continuously or remain off; overview movement need not seek audio. Selection spans time across layers and can be played or looped. A focused tutorial recalls selections through labelled boundary instants. Borrow one linked selection, independent inspection navigation and recallable study spans. Bounded live SID history, emulator-state restoration and visible lead-in/tail context are our adaptations, not features established by this review of an audio-analysis desktop tool. [Reference manual](https://www.sonicvisualiser.org/doc/reference/5.2.1/en/), [selection tutorial](https://www.sonicvisualiser.org/doc/tutorial/en/selections-inspection.html).

## Chip Player JS: reusable player and visualizer

Transport, local files, subtunes, metadata and grouped voice controls already cover substantial player functionality. Controls include chip grouping, group toggles and modifier-solo/restoration. App owns the audio graph, players, sequencer and service/UI wiring; it is not a drop-in analyser widget. [Pinned App](https://github.com/mmontag/chip-player-js/blob/e90f505ccea598fb91cf08b02c4dbb41f0785632/src/components/App.js), [voice controls](https://github.com/mmontag/chip-player-js/blob/e90f505ccea598fb91cf08b02c4dbb41f0785632/src/components/PlayerParams.js).

Visualization is format/capability-dependent: the reviewed piano-roll/chord path uses MIDI data, while linear/log FFT and Constant Q displays analyse audio. Controls include FFT size, scroll speed and on/off; spectral history scrolls canvas pixels, with updates paused by playback/disable state. Neither this raster nor MIDI note access establishes selectable SID event history or SID score extraction. [Visualizer](https://github.com/mmontag/chip-player-js/blob/e90f505ccea598fb91cf08b02c4dbb41f0785632/src/components/Visualizer.js), [Spectrogram](https://github.com/mmontag/chip-player-js/blob/e90f505ccea598fb91cf08b02c4dbb41f0785632/src/Spectrogram.js), [PianoRollEngine](https://github.com/mmontag/chip-player-js/blob/e90f505ccea598fb91cf08b02c4dbb41f0785632/src/piano-roll/PianoRollEngine.js).

The user's screenshots supplied on 2026-10-16 show a coloured piano-roll display with keyboard/chord label and a separate Constant Q spectrogram with keyboard pitch labels; the user identifies the latter input as VGZ. They also show blue panels, pixel lettering and compact controls, which the user likes as a C64-inspired direction. These are visual references, not Safari, SID-analysis or usability tests. Spectral pitch labels locate frequency bands; they do not by themselves identify score notes or instruments. Preserve the visual character while improving readability and modern interaction; the [proposal's visual direction](../design/web-player-and-analyser.md#visual-direction) owns that preference.

Further screenshots identified by the user as SID playback show the log-FFT mode and a settings panel with two MOS6581 groups, each containing three oscillator toggles, plus a speed slider. The selected theme is labelled “MS-DOS.” This confirms the visible player/visualizer and dual-chip control presentation in the supplied session, without establishing the audio routing, mute dependency semantics or emulator accuracy. The format distinction should therefore be stated narrowly: MIDI supplies the reviewed note-based visualization; SID and other formats can use audio spectral displays.

The SID wrapper exposes mixed stereo PCM, muting, tempo, subtunes and fork-provided seek, but no raw chip buses, output matrix, register access or ordered traces. Reusing the app leaves our engine boundary unresolved. Its SID loader requests external metadata by file hash and uses a 150-second fallback that ends/advances playback. App hides visualization on phones. A local/private, unknown-duration and minimally mobile-capable explorer needs different behavior. A hash request is an external disclosure, not a file upload. [SID wrapper](https://github.com/mmontag/chip-player-js/blob/e90f505ccea598fb91cf08b02c4dbb41f0785632/src/bindings/libsidplayfp-wrapper.cpp), [SID loader](https://github.com/mmontag/chip-player-js/blob/e90f505ccea598fb91cf08b02c4dbb41f0785632/src/players/SIDPlayer.js), [App](https://github.com/mmontag/chip-player-js/blob/e90f505ccea598fb91cf08b02c4dbb41f0785632/src/components/App.js).

GitHub Pages deployment is documented, with separate catalog/metadata and Firebase account dependencies. Upstream describes its own `src/` as MIT and the combined application as generally GPLv3. Referenced libsidplayfp/reSID forks carry GPL-2.0-or-later notices; the Constant Q implementation carries LGPL-2.1-or-later. Reusing UI does not make the assembled distribution MIT. This is a bounded source review, not a complete license audit. [README](https://github.com/mmontag/chip-player-js/blob/e90f505ccea598fb91cf08b02c4dbb41f0785632/README.md), [libsidplayfp](https://github.com/mmontag/libsidplayfp/blob/montag-dev-2.14/src/sidplayfp/sidplayfp.h), [reSID](https://github.com/mmontag/resid/blob/montag-dev/sid.h), [Constant Q source](https://github.com/mmontag/chip-player-js/blob/e90f505ccea598fb91cf08b02c4dbb41f0785632/src/showcqtbar.c).

## Ableton Learning Synths: explain one audible decision

“Matching envelopes” pairs familiar instruments with synthesis examples and focused parameter changes, including why decay can have no effect at full sustain. Borrow a passage card that asks the visitor to hear, select, observe and return to context. This is an educational interaction precedent, not SID evidence or justification for a complete course or editor. [Lesson](https://learningsynths.ableton.com/envelopes/matching-envelopes).

## Williams Sound Explorer: individual sound inspection

The user's scope clarification is decisive: Williams concerns individual sounds/instrument programs, so it covers part of the proposed feature set. Its linked views can inform our sound microscope and explanation cards. They do not supply the song-level experience: following form and phrase development, identifying recurring instrument roles, inspecting voice allocation over time or understanding how parts cooperate across two SID chips. Those remain central requirements, not a small extension of a single-sound viewer.

The user identified [Williams Sound Explorer and Designer](https://github.com/mbackschat/williams-sound-explorer) during this review. The public README and clean local checkout at commit `4904543d564da982ddc2242b771f27ef19a68dd0` were inspected, including the manual, pedagogical design, source and stored hero image. No application was run. The repository describes local-only ROM loading, a browser explorer and a separate design mode; the README names Chrome and Firefox. It is therefore an existing project-specific reuse opportunity, not evidence that Safari or SID support is already solved. [README](https://github.com/mbackschat/williams-sound-explorer/blob/main/README.md).

Its most relevant principle is multiple representations of the same instant: sound, visible state and code. The documented explorer includes routine swimlanes, byte history, parameter displays, source references, listening interventions and explanation cards. The stored UI image shows dark, labelled panels, consistent engine colours, ordinary buttons/sliders and collapsible help. Borrow that explanatory organization without copying all panels into the SID landing view. The SID adaptation should emphasize song form, instruments and physical chip allocation before assembly details. [Pedagogical design](https://github.com/mbackschat/williams-sound-explorer/blob/main/docs/design/pedagogical_design.md), [stored interface image](https://github.com/mbackschat/williams-sound-explorer/blob/main/docs/img/readme/hero.png).

The source provides concrete reuse seams. `ExplainerCard` separates summary, mechanism, what to watch, code references and related material, with explicit missing/idle states. `CodePanel` accepts an inspection cursor distinct from live CPU state; spectrogram/byte-tape selection resolves a cycle to a recorded PC at-or-before it. Adapt those ideas to pinned click/touch selection, evidence coverage and optional source links. A nearby recorded instruction is useful attribution, but temporal correspondence alone does not prove that instruction caused a spectral feature—especially for a stateful SID filter or oscillator. Exact program attribution requires matching trace/source evidence. [Cards](https://github.com/mbackschat/williams-sound-explorer/blob/main/explorer/src/viz/ExplainerCard.ts), [code panel](https://github.com/mbackschat/williams-sound-explorer/blob/main/explorer/src/viz/CodePanel.ts), [selection wiring](https://github.com/mbackschat/williams-sound-explorer/blob/main/explorer/src/web/main.ts).

The tape scrubber replays captured DAC events without re-running the CPU, with separate RAM snapshots for historical inspection. Its finite history clips evicted segments and maps cycles into real-time or compact timelines. These are useful history/navigation patterns, not complete emulator snapshots or state-preserving SID seek. Preserve real musical timing in the SID timeline; removing quiet gaps would change how the arrangement reads. Reverse replay and instruction stepping are not initial SID requirements. [Manual, tape-scrubber tutorial](https://github.com/mbackschat/williams-sound-explorer/blob/main/MANUAL.md), [scrub timeline source](https://github.com/mbackschat/williams-sound-explorer/blob/main/explorer/src/engine/scrubTimeline.ts), [implementation account](https://github.com/mbackschat/williams-sound-explorer/blob/main/docs/implementation/explorer_implementation.md).

The application and documentation carry MIT terms; ROMs and third-party components remain separate. Its headless-core/browser separation and shared observation contracts are useful architectural references, not a reason to select its TypeScript/Vite/canvas stack now or reuse its 6802 emulator for SID. Inspect component coupling before proposing extraction; no portability effort was measured. Keep its full sound designer, ROM export, instruction stepping and quizzes outside this proposal. [License](https://github.com/mbackschat/williams-sound-explorer/blob/main/LICENSE), [architecture](https://github.com/mbackschat/williams-sound-explorer/blob/main/docs/implementation/explorer_architecture.md).

**Recommendation:** treat Williams as a component/reference source for individual sound inspection and Chip Player JS as a player-shell candidate. Neither supplies the complete arrangement analyser. Use tracker overview/occurrence navigation, linked passage study and our existing SID research to design the song-level layer. Add concise “what to hear / what to watch / why / evidence” cards and event-to-source navigation where supported; do not assume two complete applications should be merged. Synchronized sound inspection has a direct precedent, while the proposed combination must still earn its value through musical exploration.

## Selected lessons and alternatives

| Lesson | Rationale | Proposal owner |
| --- | --- | --- |
| Retain selectable observations and an independent inspection cursor. | A fleeting attack should remain inspectable after it passes. | [Selection and retained history](../design/web-player-and-analyser.md#selection-and-retained-history). |
| Link known programs to occurrences and recipes; keep unknown events observational. | Makes reusable knowledge useful without inventing identities for local files. | [Main interactions](../design/web-player-and-analyser.md#main-interactions). |
| Recall phrase spans with audible context and consistent state. | A sound's role depends on entrances, tails and accompaniment. | [Seeking and loops](../design/web-player-and-analyser.md#seeking-and-loops). |
| Put stable chip/voice identities and shared resources beside mute/solo. | Enables attribution without suggesting independent filters, native per-voice pan or additive stems. | [Voice controls and stereo](../design/web-player-and-analyser.md#voice-controls-and-stereo). |
| Explain one audible decision per evidence-linked card. | Gives research a useful entry point without overwhelming the listener. | [Music views](../design/web-player-and-analyser.md#views-that-explain-the-music). |

Evaluate Williams' components for the sound-inspection portion. Prefer a pruned Chip Player JS adaptation if existing player integration remains useful after replacing service dependencies and extending the SID boundary; prefer a smaller project layer if those changes create more coupling than reuse saves. Both routes still need the song/arrangement analysis layer. DeepSID becomes more attractive if its collection-browser scope is desired and permission/static-local constraints can be resolved. Effort savings have not been measured; no source-only review settles the choice. The decisive checks remain correct MOS6581/MOS8580 single/dual-SID playback and routing, observation access, seeking, privacy and Safari behavior.

Defer arbitrary pane editors, plugin hosting, automatic cross-performance alignment, exhaustive FFT controls, accounts and a full synthesis curriculum. They expand scope without directly closing the project's instrument/arrangement gap. The selected refinements are product judgments, not validated UX or automatic instrument-decoding guarantees.
