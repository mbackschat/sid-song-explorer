# SID analysis capabilities and headless feasibility

**A standalone Node analyser is feasible using Explorer's existing `SidSession` and verified SIDLite runtime.** Its strongest initial output would explain how a selected performance programs its voices and shared chips, how the rendered signal changes, and exactly which interval and configuration were analysed. Static inspection adds file declarations; optional offline databases add curated context. Neither layer generally recovers the original score, instruments or arrangement. Recommend a bounded streaming report over the currently supported callable PSID subset, without a new emulator, runtime rebuild or separate package extraction. This is research preparing a proposal, not an accepted feature contract or an implementation claim. ([Session](../../src/engine/session.ts), [existing architecture](../architecture/playback-adapter.md))

Research checked **2026-10-20**, against Explorer source baseline `20882576deb4a1b3645d1887f86ce5bffcc3ac35`. Evidence comprises local source/test inspection, retained previous validation and primary upstream documentation; no new emulation, benchmark, build or listening test was run. The adopted wrapper is `libsidplayfp-wasm` 1.1.0, source `c9622e9ce7ffa2ddd3e0568e987b4c6614da8275`, containing libsidplayfp `732fa8ec8131fc75aafc2eaea583ddcdeea2a3cc`. Moving upstream links below are dated research observations, not adoption pins. ([Source ownership and licenses](../../THIRD_PARTY_NOTICES.md), [retained completion audit](../PLAN.md#implementation-completion-audit))

## File declarations establish context, not musical structure

Classic SID files contain a C64 program and startup information rather than a standardized musical document. Keep five evidence classes visibly distinct: **declared** file values, **curated** external records, **observed** emulator behavior, **calculated** measurements and **heuristic** interpretations. Also distinguish raw declarations from loader normalization and the configuration actually selected for execution. A valid header does not establish successful playback or musical correctness. ([Classic format](https://vice-emu.sourceforge.io/vice_17.html), [loader normalization](https://raw.githubusercontent.com/libsidplayfp/libsidplayfp/master/src/sidtune/SidTuneBase.cpp))

| Static inventory | Useful result | Limit |
| --- | --- | --- |
| Container and layout | PSID/RSID, version, file/payload size, data offset, load/init/play addresses, validation findings | A zero load address delegates to the payload's little-endian prefix; retain raw and effective values. |
| Subtunes and timing | Count, default subtune, VBI/CIA declaration | Timing declaration is not BPM or meter. |
| Descriptive metadata | Name, author, released text | File-supplied strings, not verified attribution. |
| Hardware and compatibility | Clock/model flags, additional SID addresses, MUS/BASIC/compatibility flags, relocation fields | Version-dependent declarations; unknown/both values do not select a unique playback profile. |

These are container fields, not an instruction to execute arbitrary contents. RSID specifically covers programs requiring a fuller C64 environment; static recognition and runtime acceptance are separate capabilities. ([VICE format reference](https://vice-emu.sourceforge.io/vice_17.html), [HVSC FAQ](https://hvsc.c64.org/faq))

**The official format now includes v5**, revised 2026-10-09. It changes existing field meanings: variable metadata, multi-SID configuration up to 15 chips, shared model/panning declarations, optional appended per-subtune lengths and an FM OPL flag. A v4 decoder must not silently interpret those fields as its own layout. Embedded duration is a declaration, not proof that execution terminates. Upstream libsidplayfp added v5 parsing on 2026-10-15 in `3d18c55317c0756d843d85033352326d1dd78b73`; that change still limits playback to three SIDs and rejects FM OPL. This establishes source support, not support in Explorer's adopted binary. ([Current specification](https://hvsc.c64.org/download/C64Music/DOCUMENTS/SID_file_format.txt), [permanent upstream change](https://github.com/libsidplayfp/libsidplayfp/commit/3d18c55317c0756d843d85033352326d1dd78b73))

Explorer currently accepts **callable PSID v1–v4, one or two chips**, with explicit subtune, PAL/NTSC and MOS6581/MOS8580 choices. It rejects RSID, MUS, PlaySID-specific profiles, third chips and interrupt-driven `play=0`; its bounded startup probe can also reject delayed-start programs. One selected model applies to both chips. This narrower boundary is the recommended first execution scope; newer-format static decoding would be an explicit additional choice. ([Actual preflight and configuration](../../src/engine/session.ts))

The general container exposes no common original note list, pattern/order format, instrument table or tempo map. Specialized player/editor decoders can recover more, but register-derived notes or sound-setting clusters must not be called recovered composer instruments. Classic v1–v4 headers also lack duration; v5's optional declaration does not solve automatic end detection. These are limits inferred from the format contract, not a claim that all specialized recovery is impossible. ([Classic format](https://vice-emu.sourceforge.io/vice_17.html), [v5 specification](https://hvsc.c64.org/download/C64Music/DOCUMENTS/SID_file_format.txt), [Explorer evidence semantics](../design/web-player-and-analyser.md))

Optional offline enrichment can make reports much more useful:

| Source | Contribution | Matching and provenance |
| --- | --- | --- |
| HVSC `Songlengths.md5` | Reference durations by subtune | Modern MD5 covers the entire original file, including header; preserve database revision, match and subtune. Legacy `Songlengths.txt` uses a different fingerprint. ([Official FAQ](https://hvsc.c64.org/download/C64Music/DOCUMENTS/Songlengths.faq)) |
| HVSC STIL | Historical comments, credits and covered-work information | Uses HVSC paths and optional subtune entries; distinguish SID author from covered-work artist. ([STIL FAQ](https://hvsc.c64.org/download/C64Music/DOCUMENTS/STIL.faq)) |
| HVSC BUGlist | Known rip defects or incompleteness | Path-based editorial evidence; absence is not a clean bill of health. ([Official list](https://hvsc.c64.org/download/C64Music/DOCUMENTS/BUGlist.txt)) |
| SIDId signatures | Likely playroutine family | Byte-pattern matches with uncertain coverage/correctness; preserve signature version and multiple matches. ([SIDId](https://github.com/cadaver/sidid)) |

**Local files, hashes and metadata matching must remain device-local.** No automatic online lookup follows from this research. User-supplied versioned databases are a sensible optional route; preserve ambiguous path matches rather than joining by basename. Redistribution rights for bundling those databases/signature collections were not established. ([Privacy and publication owner](../../CLAUDE.md#evidence-and-publication))

## Execution offers strong metrics when interpretation stays explicit

`SidSession` already returns ordered writes with chip, register, value, raw cycle and calibrated time; delivered PCM frame bounds; last-written register images; and dropped-record counts. PCM is 44,100 Hz signed Int16, with one output for mono or chip-order interleaved outputs for dual SID. This is a stronger foundation than scraping the sampled browser overview. The inspector already decodes many relevant controls, while the audio monitor supplies existing peak/RMS calculations. The following matrix is a recommended analysis inventory, **not implemented batch functionality**. ([Session](../../src/engine/session.ts), [inspector](../../src/ui.ts), [audio monitor](../../src/audio-monitor.ts))

Here **O** means observed in the chosen execution, **C** means deterministically calculated, and **H** means heuristic. Reliability always assumes stated coverage and valid source observations.

| Level / useful output | Method | Reliability and material limit |
| --- | --- | --- |
| Voice: programming activity | Count writes, value changes, gate rises/falls and first/last writes; summarize in time bins | O/C. Register activity is not audible polyphony or note count; a held sound needs no repeated writes. |
| Voice: sound-control profile | Time-weighted waveform combinations, ADSR settings, pulse-width ranges and transitions | C. Preserve combined waveform bits; settings are neither instantaneous envelopes nor original instruments. |
| Voice: programmed pitch motion | Frequency-word range/histogram; oscillator Hz; optional nearest-note/cents mapping and stable intervals | C for conversion, H for musical events. Declare clock/tuning; zero has no logarithmic pitch. Noise, ring/sync and split-byte updates complicate heard-note interpretation. |
| Voice/chip: modulation and filtering | Ring/sync/test occupancy; chip cutoff/resonance trajectories, modes, routing, volume and V3 direct-off intervals | O/C. Report cutoff register units; enabled controls do not establish audible strength or a universal acoustic cutoff curve. |
| PCM/output: levels and quiet intervals | Windowed peak, RMS, DC mean, sample extrema and threshold-defined quiet spans | C for this renderer/output tap. Extrema are possible saturation evidence, not proof of analogue clipping or perceived loudness. |
| Dual-chip PCM: balance and similarity | L/R energy difference, normalized correlation, optional mid/side energy | C. Describe the output matrix; neither intended panning nor independent voice stems follows. |
| Song structure: entrances and changes | Compare aligned bins of control states, activity, pitch bands and PCM energy | C descriptors, H section/role labels. A silent modulator matters; a register change need not begin a section. |
| Song structure: repeated material | Compare relative-timed write segments or coarser feature sequences; return interval pairs | C equality in a named representation, H motifs/phrases. A repeated segment is not proof of a loop or song end. |
| Optional PCM timbre | Windowed band energies, centroid, flatness or bounded spectrogram | C with explicit FFT/window/hop settings. Full-chip features mix voices; centroid is not pitch and flatness does not identify the SID noise bit. |
| Deferred digi classification | Inspect D418 rates and dense frequency/pulse/control bursts | O/C evidence, H classification. Volume automation can resemble digis; absence of volume activity cannot exclude other techniques. |
| Deferred CPU/driver cost | Existing write cadence now; instruction/routine metrics require different instrumentation | Write timestamps reveal intervals, not CPU utilization or routine cycle cost. |

The hardware basis is the SID's programmed frequency/control/ADSR registers and chip-shared routing/filter/volume; oscillator frequency follows `frequencyWord × chipClock / 2²⁴`. Envelope history and coupled oscillators explain why visible settings do not fully describe sound. Spectral and recurrence methods are established mathematical descriptors, but no corpus evaluation here establishes their musical classification accuracy. ([Original Commodore datasheet reproduction](https://www.waitingforfriday.com/?p=661), [envelope implementation](https://github.com/libsidplayfp/libresidfp/blob/main/src/EnvelopeGenerator.cpp), [spectral flatness](https://librosa.org/doc/0.11.0/generated/librosa.feature.spectral_flatness.html), [recurrence definition](https://librosa.org/doc/0.11.0/generated/librosa.segment.recurrence_matrix.html))

Use **time-weighted summaries**, not write-weighted approximations: rewriting an unchanged setting every frame should not outweigh holding that setting for the same duration. Report gate state, waveform selection, register activity and chip energy separately instead of an undefined “active voice” count. Preserve same-timestamp order and prior state across chunks. These recommendations follow from the session's ordered-write contract. ([Trace contract](../architecture/playback-adapter.md#pcm-trace-timing-and-coverage))

Snapshots can miss rapid off/on transitions, intermediate changes and repeated writes. Gate edges are envelope-control events rather than exact audible note boundaries. Shared filters and ring/sync dependencies also mean muted/solo renders are labelled interventions, **not generally isolated stems**; intervention can alter writes before the trace hook. Repeated register images omit oscillator, envelope and broader C64 state, so neither repetition nor silence certifies a song end. ([Design contracts](../design/web-player-and-analyser.md), [pinned trace-hook basis](https://github.com/chrisgleissner/libsidplayfp-wasm/blob/c9622e9ce7ffa2ddd3e0568e987b4c6614da8275/MODIFICATIONS.md), [SID state implementation](https://github.com/libsidplayfp/resid/blob/master/sid.cc))

## Node reuse preserves stronger evidence than a new execution path

`SidSession` has no browser/bundler dependency. Existing Node guards load the prepared custom runtime and check mono/stereo PCM, ordered writes, chip ownership and continuation against independent raw-library results. Retained validation supports feasibility; it does not establish an implemented CLI or arbitrary-file throughput. Consume the session directly for sequential analysis, bypassing `CachedSidSession` because its history/seek cache solves a different problem. No rebuild is necessary when the verified runtime is already prepared. ([Node engine guards](../../tests/engine.test.ts), [stereo guards](../../tests/stereo-engine.test.ts), [runtime verification](../../scripts/prepare-runtime.ts))

| Existing option | What it contributes | Why it is not the whole proposed analyser |
| --- | --- | --- |
| Explorer `SidSession` | Profile-controlled PCM plus ordered writes and loss/coverage information | Best consistency with Explorer; orchestration, aggregation and reports still need implementation. |
| Native sidplayfp/libsidplayfp | Console playback, WAV export, bounded duration/profile controls; CPU dumps in debug builds | Valuable reference or broader-profile route, but native/debug/ROM setup and matching configurations need separate validation. ([Official CLI documentation](https://github.com/libsidplayfp/sidplayfp/wiki/sidplayfp)) |
| SIDDump 1.11 | Three-channel register/note-oriented rows and `-z` CPU profiling | Useful lightweight comparison for suitable callable players; its own help warns about CPU/illegal-opcode limits. Per-frame output is not Explorer's dual-chip ordered-write/PCM contract. ([Official source](https://github.com/cadaver/siddump/blob/master/siddump.c)) |
| SIDId 1.09 | Static byte-signature player identification | Optional context, not execution, musical-data decoding or proof of authorship. ([Official repository](https://github.com/cadaver/sidid)) |

These tools were inspected, not installed or executed. The adopted WASM surface does not expose general RAM traces, instruction/PC streams or routine profiling. Native libsidplayfp debugging demonstrates a possible extension route; switching to the alternative reSIDfp sound engine alone does not provide that instrumentation. Broader RSID/ROM, v5 or third-chip support is separate compatibility work. ([Pinned binding](https://github.com/chrisgleissner/libsidplayfp-wasm/blob/c9622e9ce7ffa2ddd3e0568e987b4c6614da8275/src/bindings/bindings.cpp), [session surface](../../src/engine/session.ts), [upstream C++ API](https://libsidplayfp.github.io/libsidplayfp/html/classsidplayfp.html))

Streaming makes the first scope practical without retaining whole-song audio/history. Ten minutes of two-channel Int16 PCM at 44,100 Hz alone occupies 105,840,000 bytes; peak/RMS/state counters do not require keeping it. Detailed traces should likewise be optional, capped and streamed. Dense recurrence grows quadratically, so coarse or bounded comparisons belong after direct summaries. These are sizing consequences, not measured memory/throughput claims. ([PCM representation](../../src/engine/session.ts), [recurrence matrix shape](https://librosa.org/doc/0.11.0/generated/librosa.segment.recurrence_matrix.html))

Existing per-operation deadlines and bounded raw calls are useful but do not supply a whole-job budget or interrupt a synchronous WASM call. A headless job needs explicit total work/output limits; hard cancellation requires an external worker/process boundary. Preserve the current internal render partition and calibration: this SIDLite pin is partition-sensitive, and its PCM-relative timestamps use a calibrated quantized clock rather than simple nominal-clock division. ([Bounds and timing](../architecture/playback-adapter.md))

## A small first scope can prepare a credible proposal

Recommend a report for **one selected subtune/profile and a finite requested duration**, comprising static inventory, supported-profile validation, per-voice programming/sound-control summaries, shared-chip filter/modulation summaries, coarse aligned time bins and PCM level statistics. Present representative timestamps for follow-up listening in Explorer. Deterministic summaries should deliver value before motif detection or musical labels become dependencies.

| Scope decision | Recommendation and reason |
| --- | --- |
| Required evidence | Input identity; requested/resolved subtune, clock and model; chip addresses/order; engine/runtime identity; sample format/output tap; startup/resampling/digi/mute/filter configuration; timing basis and render partition. These make measurements comparable. |
| Required completeness | Actual frame interval, requested bound, stop reason, truncation/failure and dropped writes. Counts with lost events are lower bounds; state-duration metrics can become unreliable beyond a lost transition. |
| Optional next steps | User-supplied offline metadata, capped trace/PCM export, multiple separately budgeted subtunes, pitch-motion/repeat candidates and spectral descriptors. Add only when the first report reveals a concrete need. |
| Excluded initially | Universal score/instrument recovery, certified end/loop detection, stem recovery, CPU profiling, broader C64/ROM compatibility and musical-quality judgments. The available interface does not substantiate them. |

Reference duration, file-declared duration and analysed duration must remain separate. Reaching a bound means the requested observation finished; it does not prove the song finished. Equally, rendered PCM and retained automated tests establish software behavior, not physical-SID equivalence, real Safari playback or human musical acceptance. ([Evidence owner](../../CLAUDE.md#evidence-and-publication), [existing trace coverage](../architecture/playback-adapter.md#pcm-trace-timing-and-coverage))

Before implementation is accepted, the appropriate independent guard is agreement between streaming summaries and complete short traces/PCM, including chunk boundaries, redundant writes, rapid gate changes and chip-global routing. Heuristic additions need labelled examples and measured false positives. Throughput, peak process memory, dense-write behavior and broad corpus compatibility remain unmeasured. Distribution should retain the existing corresponding-source/notices/provenance mechanism; this research establishes no additional rights to music, ROMs or metadata collections. ([Existing raw-runtime gates](../../scripts/experiments/stereo/README.md), [third-party notices](../../THIRD_PARTY_NOTICES.md))
