## Centered timeline spike (`TIMELINE-1`)

On 2026-10-19 the user requested upcoming activity in the main voice timeline, with the moving heard playhead centered and approximately equal past/future space. They prioritized checking this idea through a bounded POC/spike before the next work item. The original spike kept the existing ten-second Scroll scale: five seconds before and five seconds after the heard position. Fit history remains a separate overview. A configurable split was excluded. Zoom was initially excluded and subsequently requested as the separate follow-up below.

The initial source inspection identified two constraints: [the following window](../src/timeline.ts) placed the playhead at the trailing edge after startup, and [the UI](../src/ui.ts) clipped observations at the heard position. [The worker](../src/engine/worker.ts) already prepared future audio and ordered register writes in [the bounded cache](../src/engine/cached-session.ts), but the UI received only its coverage and the observations accompanying scheduled audio. Reusing those prepared observations is the recommended feasibility route; source inspection alone does not establish a working preview or its performance.

The spike's required behavior and acceptance gates are:

- Keep the heard playhead centered in Scroll, including startup and the ending; shade time outside the tune or available observations. Show real emulated upcoming activity and distinguish it from heard history. Do not extrapolate missing data or delay playback until the future half is filled.
- Preserve Hold/Resume and inspection independent of playback. A selected upcoming moment must use retained prepared observations with their coverage and configuration; it must not be labelled already heard. Fit history retains its history semantics.
- Keep playback, fast seeking and existing cache bounds intact. Refresh or invalidate preview data after seeks, mute/solo, profile changes and tune replacement. At a loop boundary, distinguish the impending repeat from linear song material that will not be heard next; wrapped preview is outside the first spike.
- Use continuous rendering as the independent oracle for upcoming register/write data and unchanged PCM. Add red/green guards for the centered window, partial/unavailable coverage, stale observations and read-only access that preserves playback/producer positions. Measure added memory and refresh cost without relaxing existing limits.
- Verify centered drawing, visible upcoming activity, held inspection, seek/mix transitions, narrow layout and advancing playback in silent Chrome/macOS WebKit. Present the rendered preview for the user's usefulness verdict. Record the evidence and integrate/defer recommendation before returning to `VOICE-1`; a broader playback redesign requires a separate scope decision.

Status: the bounded preview is implemented locally; [the validation record](validation/mono-poc.md#centered-timeline-spike) retains correctness and cost evidence. The user confirmed it works but reported jumpy filling at the right edge. A regression reproduced that defect in both supported browsers; an extra second of off-screen observations now covers motion between refreshes. On 2026-10-19 the user confirmed “Yes, fixed,” accepting the corrected preview. Automated browser and full-song playback checks passed. Decision: integrate the bounded implementation. The implementation reuses prepared observations without a playback redesign. This spike does not reopen the accepted mono POC or close `VOICE-1`.

## Timeline zoom (`TIMELINE-2`)

After accepting `TIMELINE-1` on 2026-10-19, the user requested zoom/unzoom and specified that equal zoom means equal time density: if width W shows N seconds, width 2W must show 2N seconds. This supersedes the spike’s fixed ten-second viewport. The drawable timeline width excludes voice labels and side panels.

Required: zoom in/out changes time density by a factor of two across seven levels; resizing preserves the selected density. Live playback stays centered with equal past/upcoming space. Zooming or resizing a held view centers its selected cursor and preserves its captured observations, shading anything outside that capture. Fit history remains the retained-heard overview. Preview refreshes remain read-only, throttled and bounded, with an off-screen margin for smooth scrolling. Pinch/wheel gestures, persistent preferences and a configurable past/upcoming split are excluded.

Status: the initial zoom was implemented and verified locally. The user then requested a larger range: the follow-up extends zoom to eight times closer and twice as far out, retaining the default density. The expanded range passed focused unit checks, build and Chrome/macOS WebKit regression checks. [The validation record](validation/mono-poc.md#timeline-zoom) owns red/green, resize, playback and cost evidence. `TIMELINE-3` follows this bounded addition, before `VOICE-1`.

## Unified timeline and transport (`TIMELINE-3`)

On 2026-10-19 the user accepted the diagram of a shared transport/timeline panel with an attached proportional scrollbar and requested a functional browser POC. They subsequently required live updates while dragging, with the impression of one continuous timeline, and a button to return to the current heard position centered.

Required: one playback/zoom toolbar, voice mute/solo beside their lanes, and a scrollbar attached below the time ruler. Its nominal thumb fraction is visible duration divided by song duration; zoom and panel resizing change this ratio. Dragging the thumb, clicking the trough, arrow buttons and keyboard navigation browse without seeking. A normal voice/filter timeline click seeks playback, releases held inspection and resumes following; Shift-click inspects the chosen point without seeking. Hold captures the current heard position without pausing sound. The ruler also seeks on release. Follow releases held inspection and browsing, centers the current heard position and resumes automatic following. Held inspector data remains captured when browsing another passage. Setup, loop editing and extended help expand on demand. Routine live-status/instruction rows are hidden; pending operations, errors, ending explanations, held details and trace warnings remain visible. The redundant navigation slogan is removed.

During Follow, startup/ending may extend outside the tune to retain the centered playhead. The scrollbar clamps its position at these edges while keeping its nominal ratio; manual browsing constrains the viewport to the song. A view larger than the song uses a full disabled thumb. Local files with unknown duration use the labelled explored range. Fit history keeps its existing semantics and disables manual scrolling until Scroll is selected.

The POC renders on pointer movement and reuses same-configuration observations while requesting nearby prepared data. Missing or unprepared observations remain shaded; continuous browsing does not imply unlimited retained data or extra emulation. [The validation record](validation/mono-poc.md#unified-timeline-panel) owns guards, performance scope and browser evidence. Status: local implementation verified, with final user layout/interaction review pending. Public deployment and `VOICE-1` are outside this POC.

## Bounded live-voice prototype

On 2026-10-19 the user authorized a bounded prototype and automatic integration only if it works with limited change scope. Success requires unchanged full-mix PCM, prompt sustained-note output switching without restarting oscillator/envelope execution, preserved shared-filter behavior, and compatibility with fast seeking and bounded storage. The silent native trial is complete; [the owning study](research/seek-performance.md#bounded-live-gain-prototype-and-integration-decision) retains the reproducible runner, passing selective-gain checks and integration decision. Do not substitute delayed replacement-mix preparation for this live-control trial. Human listening remains a separate gate.

Native output gains passed the bounded fixtures, but preserving prepared seeking exceeds the limited-scope condition: the minimum design crosses WASM packaging, raw-buffer alignment, cache storage, filter-history semantics and playback scheduling. Three lossless Int16 voice signals alone require 48.79 MiB for the current sample, beyond the existing 32 MiB cache cap. That bounded trial did not integrate production playback. The user subsequently authorized continuing toward production, then explicitly permitted a spinner with an explanation if uninterrupted switching is infeasible or too costly. The current correction uses that fallback because integration crosses six coupled audio boundaries; [the retained cost decision](research/seek-performance.md#production-feedback-fallback-and-follow-up) owns the assessment. The interruption remains unresolved and is tracked as `VOICE-1` below; shipping feedback does not close it.
